# 全画布扩散 vs 块扩散：它们"停"的方式不同，所以 merge 的规律也不同（2026-10-06）

**独立结论文档。** 全部数字来自磁盘上已有的产物，零 GPU。
过程、弯路和被撤回的说法在 `../CONFIDENCE_CHANNEL.md`（那是日志，不是结论）。
脚本：`../details/draft_scripts/`（`traj_table.py`、`why_eosshare.py`、`dreamreasoner.py`、`full_table.py`）。

---

## 1. 两种架构"停"的机制（实测，不是推断）

| | **全画布扩散**（Dream-v0, DiffuCoder, LLaDA） | **块扩散**（DreamReasoner b32, Nemotron b8, SDAR, TraDo） |
|---|---|---|
| 机制 | 没有 halt。画布固定（如 512 格），每格都必须填。"停" = **EOS padding 从哪一格开始** | emit EOS → 填完当前 block → **整个生成 halt** |
| 实测证据 | 已提交位置 = **100.0%** 的画布（512/512） | 已提交位置是**连续前缀**，**500/500** 道题；只占 8192 的 **11.7%**（中位生成 407，均值 959） |
| 每题 EOS 个数 | τ_A=0 → **247**（半张画布是 padding）；τ_A=1.1 → **1** | 中位 **16**，而 block 长度 32 → **正好半个 block**（答案在 block 中间写完，补满该 block 再 halt） |

→ **"EOS 占提交的比例"这一列不能跨架构比。** 块扩散的分母被"从没访问的格子"稀释（1.8% 看着像没有，
其实是 17 个正常的收尾标记）。可比的列是**顶cap**、**有EOS的题数**、**平均生成 token**。

## 2. 丢掉 EOS 的代价，两种架构差一个数量级

| | 全画布（Dream-v0, MATH-500 @512, 官方, n=500） | 块扩散（DreamReasoner, MATH-500 @8192, n=500） |
|---|---|---|
| EOS 行为被破坏时 | 每题 EOS 247 → **1**，顶cap 14.4% → **93.8%** | 有EOS的题 487/500 → **4/500**，生成量 959 → **8137** token |
| 准确率 | **39.6 → 51.0（涨了 11.4）** | **89.2 → 70.4（掉了 18.8）** |
| 算力 | 不变（512 格本来就全付） | **8.5 倍** |
| 为什么 | 官方 scorer 在整条 512 token 里找 `\boxed{}`，所以"顶cap" ≠ "没答上"（那个 arm 写完率 92.6%） | 不 halt 就把预算跑满，既费算力又真的答不对 |

## 3. 最佳 merge 形式也因此不同（论文 `tab_ablation.tex` + 磁盘上的数）

| 家族 | 架构 | 凸组合 `D_b+(1−β)τ_D+βτ_A` | direct addition `D_p+βτ_A` | 谁赢 |
|---|---|---|---|---|
| Dream-v0 / IFEval | 全画布 | 72.8 (β=0.6) | **77.1** (β=1.1) | **direct addition +4.3**（论文自己加粗了） |
| Dream-v0 / MATH-500 | 全画布 | 45.0 (β=0.6) | **51.0** (0.9τ_D+1.1τ_A) | **direct addition +6.0**（**论文未报此列**） |
| DreamReasoner / MATH-500 | 块 b32 | **91.6** (β=0.2) | 91.4 (β=0.3) | 凸组合（+0.2，基本平手） |
| Dream-Coder / HumanEval | 全画布 | **84.8** (β=0.2) | 83.5 (β=0.4) | **凸组合 —— 这是反例** |
| DiffuCoder / HumanEval | 全画布 | **79.3** (β=0.2) | 73.8 (β=0.6) | **凸组合 —— 这是反例** |

### ⚠️ 诚实的边界
架构二分法在**机制**上是实测成立的（§1、§2）。但它**不足以预测哪个 merge 形式赢**：
**Dream-Coder 和 DiffuCoder 也是全画布，却是凸组合赢**（84.8 vs 83.5；79.3 vs 73.8）。
所以不能写成"全画布 → direct addition 赢"。下一步该查的是这两个 coder 家族的收尾/写完行为
（它们的产物也在磁盘上），看看是不是代码任务的长度需求不同。

## 4. (τ_D, τ_A) 曲面：不需要搜索，因为是平台

29 个官方 IFEval arm，**协议完全一致**（1280 token / 1280 步 / T=0.1 / top_p 0.9 / entropy / 全集，
`limit=None`），指标 inst-level strict acc：

| 区域 | IFEval inst-strict |
|---|---|
| **τ_D = 0**（τ_A 0.5→0.9，5 个点） | **62.9 – 63.8**，平的，灾难 |
| **凸组合线** τ_D+τ_A = 1（(0.5,0.5),(0.3,0.7)） | 74.2 / 75.9 |
| **τ_D ≥ 0.68 且 τ_A ∈ [0.8,1.4]**（17 个点） | **77.6 – 79.6**，2 分带宽的**平台** |
| τ_D+τ_A = 2.6 | 75.7，开始掉 |

峰值 **79.6 @ (0.9, 1.1)**；**(1.0, 1.1) = 79.5，与 29 次实验的最优只差 0.1。**

两个支配量，**跑之前就能定**：
- **τ_D 必须保住**：τ_D=0 → 63；τ_D≥0.68 → 76–80。这是**悬崖**不是梯度。
- **τ_D + τ_A ≈ 2**：<1.5 → 74.8；1.6–2.4 → 平台；2.6 → 75.7。

→ **"快速定位"的答案是"不要搜"：τ_D=1，τ_A≈1.1，一个点就落在平台里。**
论文自己也写了 "a plateau over [0.9,1.4]"。

### 指标对账（防止以后又对不上）
论文 ablation 的 IFEval 77.1 = 四个 IFEval 指标的平均：
prompt/inst × strict/loose = 72.1 / 79.5 / 75.0 / 81.9 → 平均 **77.1**。
本文件的 §4 用的是 **inst-level strict**，所以数值比论文高约 2.4–3.6 分，趋势和峰值位置一致。

## 5. 无标签筛选：只有弱证据，不要当方法用
用**写完率**（正则抓 `\boxed{}`，不需要答案）筛 6 个 MATH-500 点：
挑写完率最高的（93.8% → (1.0,1.1)）得到 acc 50.0 —— 比真最优 51.0 差 1.0，比凸组合最佳 45.0 高 5.0。
Spearman ρ(写完率, acc) = **0.71**，n=6。失效模式正好是凸组合那两个点（写完率低但写完acc 高）。
→ **是"筛子"不是"选择器"，n=6 太少，现在不能当结论。**

# 追加（2026-10-06 晚）：用户提的 pipeline，以及 §3 那个 coder 反例的消解

## 用户的想法（2026-10-06）
> "最好的 pipeline 应该用 best rescaling，然后在这个基础上加上 ar vectors，最终一个问题就是可能会导致
> 一些 overmerge，但是 best rescaling 是一个合理的出发点"

形式化：`D_b + α*·τ_D + β·τ_A`，其中 **α\* 先由 self-rescaling（`D_b + α·τ_D`，不含 AR）单独定出来**，
然后再扫 β。三条线的关系：

| 形式 | 约束 | |
|---|---|---|
| 凸组合（A2D 主方法） | α = 1 − β | 两个系数**绑死** |
| direct addition | α = 1 | 不 rescale |
| **用户的 pipeline** | **α = α\***（self-rescaling 最优，实测 0.7–0.9） | **解耦，且 α 先定在自己的最优处** |

## 证据 1：self-rescaling 的最优 α 一致地略小于 1，且一致地打赢 parent
论文 `tab_ablation.tex` 的 Self-rescaling 行（五个 family/task cell）：

| 家族 | α\* | 分数 | parent | 差 |
|---|---|---:|---:|---:|
| Dream-v0 / IFEval | 0.9 | 63.4 | 63.0 | +0.4 |
| Dream-Coder / HumanEval | 0.9 | 83.5 | 81.7 | +1.8 |
| DiffuCoder / HumanEval | 0.8 | 74.4 | 72.6 | +1.8 |
| DreamReasoner / MATH-500 | 0.9 | 90.2 | 89.2 | +1.0 |
| DiffuCoder-RL / MBPP+ | 0.7 | **69.6** | 66.9 | +2.7（**比凸组合 69.0 还高，论文加粗**） |

## 证据 2：α\*=0.9 这条线上的点，正好是 29 点网格的最优

| 点 | IFEval inst-strict | MATH-500 官方 |
|---|---:|---:|
| **(0.9, 1.1) ← 用户的 pipeline** | **79.6（29 点最优）** | **51.0（我们最好的 MATH-500）** |
| (1.0, 1.1) direct addition | 79.5 | 50.0 |
| (0.95, 0.55) | 74.8 | 48.6 |
| 凸组合 β=0.6 | 72.8 | 45.0 |
| (0.9, 0.0) 只 rescale | — | 39.6（parent 38.4，+1.2） |

**但"先 rescale 再加"优于"直接加"的幅度只有 +1.0（MATH-500）/ +0.1（IFEval），两个 cell —— 这一条还没立住。**
立住的是"两者都远好于凸组合"。

## 证据 3：over-merge 的上界随 α 下降而下降（用户担心的那个点，可测）
α≈0.9–1.0 时平台是 β∈[0.9,1.4]，β=1.6 开始崩（α=1.0 → 75.7）；α 压低则崩得更早：
**(0.65, 1.6) → 69.3**。→ 两个系数不该绑在一条线上，但也**不独立**：α 越小，能承受的 β 上界越低。

## §3 那个 coder "反例"消解了
磁盘上 coder 家族只有两个 checkpoint：`dcoder-00aD-06aA`（τ_D=0）和
`dreamcoderbase_plus_0.8vdreamcoder_0.2vqwencoder`。后者是**凸组合 β=0.2 → τ_D = 1−0.2 = 0.8**,
正好落在 self-rescaling 最优（0.9）旁边。

| 家族 | 凸组合 β\* | 它导致的 τ_D | 凸组合 vs direct addition |
|---|---:|---:|---|
| Dream-Coder / HumanEval | 0.2 | **0.8** | 凸组合 **赢 1.3**（84.8 vs 83.5） |
| DiffuCoder / HumanEval | 0.2 | **0.8** | 凸组合 **赢 5.5**（79.3 vs 73.8） |
| DreamReasoner / MATH-500 | 0.2 | **0.8** | 凸组合 赢 0.2（91.6 vs 91.4） |
| Dream-v0 / IFEval | **0.6** | **0.4** | 凸组合 **输 4.3**（72.8 vs 77.1） |
| Dream-v0 / MATH-500 | **0.6** | **0.4** | 凸组合 **输 6.0**（45.0 vs 51.0） |

**完美分离：β\* ≤ 0.2（τ_D 剩 0.8）→ 凸组合全赢；β\* = 0.6（τ_D 掉到 0.4）→ 凸组合全输且输得多。**

**统一说法：凸组合只在任务需要大 β 时出事，因为那时 `τ_D = 1−β` 被压垮。**
代码任务的 β\* 本来就小，凸组合白捡了一个 τ_D=0.8，所以什么都没丢 —— 它不是反例，
是"凸组合这条线碰巧穿过好区域"的情形。

### 由此得到的可证伪预言
**解耦 (α, β) 只在 β\* 大的地方有收益，在 β\* 小的地方应该是 no-op。** 目前五个 cell 全部符合。

### 检验这个预言的实验（未跑过）
`(α=0.9, β=0.2)` 在 coder 家族**从未被构造过**（磁盘上只有 τ_D=0.8 和 τ_D=0）。
预言：它应该和凸组合的 84.8 **基本打平**（因为 0.8 与 0.9 相差很小），而**不是**超过。
如果它反而大幅超过或大幅落后，上面这个统一说法就有问题。
